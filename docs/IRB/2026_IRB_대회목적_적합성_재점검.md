# 2026 IRB 대회 목적 적합성 재점검

## 1. 결론

현재 아이디어는 빅데이터 분야 대표팀 후보로 발전할 기반이 있다. 공공통계, 개인의 시간 흐름 기록, 검수 문헌, 서비스 이용 로그를 서로 다른 역할로 처리한다는 데이터 구조와 작동하는 시제품이 있기 때문이다.

다만 기존 신청서는 건강문제와 연구윤리를 설명하는 비중이 높아, 심사자가 “좋은 연구계획”으로는 이해해도 “DRIVE와 CO-SHOW까지 성장할 대표팀”으로 평가하기에는 IP와 Entrepreneurship의 증거가 부족하다. 대표팀 선발을 위해서는 다음 문장으로 중심을 이동해야 한다.

> 진료 사이의 일상 데이터를 최소 부담으로 수집하고, 출처와 불확실성이 남는 회고·질문으로 변환하는 데이터 에이전트를 만들며, 그 구조를 사용자 검증·지식재산·사업모델로 발전시킨다.

### 1-1. 간호학적 관점만으로 출발할 수 있는가

**문제정의와 데이터·평가 설계는 간호학적 관점만으로도 충분히 출발할 수 있다.** 간호는 증상 하나의 판정보다 진료 사이의 생활, 수면·활동·감정·관계, 자기관리, 도움 요청과 의사소통을 함께 다룬다. 따라서 무엇을 최소한으로 기록할지, 환자가 어떻게 자신의 경험을 확인·수정·설명할지, 위험 신호에서 언제 의료진이나 외부자원으로 연결할지를 정하는 데 간호학이 직접적인 근거가 된다.

다만 빅데이터 대표팀 평가에서 간호학적 필요성만 제시해서는 부족하다. 간호학이 **수집할 데이터와 사용자 가치, 안전성과 평가 질문을 이끌고**, 현재 구현된 기술이 이를 실제 서비스로 실행한다는 구조로 보여줘야 한다. 제품 효과를 아직 검증하지 않았으므로 특정 간호이론이나 간호과정이 기능의 효과를 입증했다고 표현하지 않는다.

### 1-2. 저장소에서 확인한 현재 개발 상태

| 영역 | 확인된 상태 | 인큐베이팅에서 남은 일 |
| --- | --- | --- |
| 모바일 기록 | 몸·감정·관계·환경·수면 입력과 사용자별 저장 구현 | 2~3분 최소기록과 50대 이상 접근성 검증 |
| 날짜·주간 흐름 | 실제 기록 기반 날짜·주간 화면과 개인의 최근 기록 대비 표시 구현 | 빈 기록 처리와 사용자 이해도 확인 |
| 과거 유사 기록 | 증상·감정·환경·시간대 겹침 검색을 모바일에 연결 | 유사 이유 설명과 회상 유용성 검증 |
| 요약·타임라인·근거 | 역할별 서버 기능과 API 구현 | 모바일 사용자 흐름 연결, 원기록 일치와 출처 표시 검증 |
| 이용 기록 | 기록 시작·완료·중도이탈을 건강 내용과 분리 저장 | 이탈 분석 화면과 개선 주기 구축 |
| 개인정보 | 사용자별 행 접근정책 구현 | 삭제·내보내기·동의 버전·접근기록을 사용자 흐름으로 검증 |
| 통합 조정 | 역할별 기능은 분리됨 | 요청에 맞는 역할 선택, 최소 자료 접근, 실패 시 대체 흐름 완성 |
| 자동 검증 | 웹·모바일 타입검사와 의료적 금지표현 점검 통과 | 전체 테스트 58개 중 문구 기대값이 오래된 1개를 정리하고 회귀검증 유지 |

9주 자료의 제공자는 서비스 구체화에 도움을 준 실제 환자인 지인 1명이다. 이는 정식 연구나 서비스 효과 검증이 아니라, 환자의 실제 생활경험을 바탕으로 기록 항목과 화면 흐름을 정한 내부 설계 참고자료로만 제시한다.

| 축 | 현재 강점 | 현재 공백 | 선발 전 보강할 증거 |
| --- | --- | --- | --- |

| Research | 진행 중 문헌고찰, 내부 탐색, 상관분석 재현 검토 | 외부 검증의 전향적 프로토콜 없음 | 5단계 검증계획, 평가항목, 분석계획, 사전검토 기록 |

| Entrepreneurship | 웹·모바일 시제품과 초기 사용자 범위가 있음 | 고객, 지불주체, 협력채널, 운영비 가설이 없음 | 사용자–고객–협력기관 구분, 사업모델 가설, 기관 인터뷰 |

## 3. 대표팀 선발 관점의 강점

1. **아이디어 단계 이상이다.** 웹·모바일 시제품과 데이터 저장·요약·검색 구조가 있어 멘토링 기간에 실증으로 이동할 수 있다.
2. **빅데이터의 역할이 분명하다.** 단순히 AI를 붙이는 것이 아니라 집단통계, 개인 종단기록, 근거문헌, 운영로그를 목적별로 연결한다.
3. **간호학과 데이터의 결합이 차별점이다.** 진료 사이의 설명 공백을 사용자 기록과 질문으로 바꾸는 문제정의가 구체적이다.
4. **안전 경계가 제품 설계에 들어가 있다.** 진단·예후·처방을 제외하고 사용자 수정권과 위험 신호 분기를 둔 점은 실제 확장 가능성을 높인다.

## 4. 탈락 위험

- 외부 데이터가 아직 없는데 9주 1인 기록을 효과 검증처럼 보이게 하는 경우
- 개인정보·심의 우려만 길게 쓰고 실제로 무엇을 언제 수집할지 제시하지 않는 경우
- 앱 기능은 많지만 데이터 품질·출처·평가 방법이 보이지 않는 경우
- 특허 가능성을 선언하면서 선행기술이나 발명요소를 제시하지 않는 경우
- 사회적 가치만 강조하고 고객·협력기관·지속가능한 운영방식을 제시하지 않는 경우
- 5페이지 안에서 표와 안전 설명이 과도해 핵심 시연 시나리오가 묻히는 경우
- 5~10명의 초기 파일럿을 ‘빅데이터’라고 과장하거나, 반대로 이후 확장 가능한 데이터 구조를 설명하지 못하는 경우

초기 파일럿은 빅데이터 규모를 만드는 단계가 아니라 변수 정의, 권한, 품질, 지속 가능성을 검증하는 단계다. 빅데이터 분야 적합성은 공공통계·종단 자기기록·근거문헌·운영로그를 연결하는 확장 가능한 구조와, 이후 기관 협력·참여자·기간 확대 계획으로 설명해야 한다.

## 5. 대표팀용 검증 시나리오

심사자에게 보여줄 핵심 시연은 한 가지로 고정한다.

1. HIRA 연령분포로 초기 사용자를 50대 이상으로 좁힌다.
2. 사용자는 하루 1회, 2~3분 이내의 최소 기록을 남긴다.
3. 에이전트는 필요한 기록과 검수 문헌만 조회한다.
4. 사용자는 출처와 불확실성이 표시된 주간 회고를 확인·수정한다.
5. 다음 진료에서 물어볼 질문을 선택해 내보낸다.
6. 서비스팀은 건강내용과 분리된 이용 로그로 부담과 이탈을 개선한다.

## 6. 인큐베이팅 종료 시 반드시 남길 산출물

- Data: 변수 사전, 출처표, 데이터 흐름도, 접근권한표
- Research: 5단계 수집·검증 프로토콜과 결과 요약
- IP: 핵심 기술요소·선행기술·공개관리 표
- Value: 사용자가 회고를 이해·수정·활용한 증거
- Entrepreneurship: 초기 사용자·고객·협력기관·비용·수익 가설
- Demo: 가상데이터로도 안전하게 재현되는 3분 시연

## 7. 최종 판정

대회 목적에는 **조건부 적합**하다. Data–Research–Value는 이미 경쟁력이 있지만, 서울대 대표팀 선발 가능성을 높이려면 IP와 Entrepreneurship을 별도 부록이 아니라 인큐베이팅의 필수 산출물로 포함해야 한다. 외부 참여자 수집은 처음부터 시행하는 것이 아니라 아래 5단계 게이트를 통과하면서 대표팀용 증거를 쌓는 방식이 적절하다.
